# Подготовка ручной разметки Junkie

Здесь находятся слепая выборка из 30 кейсов, правила формата и инструменты проверки и последующего сравнения. Заполненные аннотации, метрики и согласованный gold не включены. Исходный eval-набор не изменяется.

## Подготовленные файлы

| Файл | Назначение |
| --- | --- |
| `blind_cases.jsonl` | 30 кейсов; только id, query, context, user_id, now, timezone, fixture_id, environment_id |
| `ANNOTATOR_PROMPT.md` | Промпт для отдельного запуска предварительной агентной разметки |
| `scripts/prepare_blind.py` | Экспорт фиксированной выборки по строгому allowlist |
| `scripts/validate_annotations.py` | Проверка схемы, покрытия кейсов, документов, ACL и fixtures; позднее — целостности согласования |
| `scripts/calculate_agreement.py` | Последующий расчёт согласия A/B и отчёта из заполненных файлов |
| `scripts/test_annotation.py` | Тесты инструментов на синтетических примерах |

## Выдача заданий и независимость

Для каждого разметчика подготовить отдельную папку с `blind_cases.jsonl`, `documents.jsonl`, `corpus/`, `fixtures/` и этой инструкцией. `documents.jsonl`, `corpus/` и `fixtures/` берутся из `eval/` с сохранением относительных путей.

Не выдавать исходные `queries/dev.jsonl`, design doc, поля expected/gold/evidence_hint, чужую разметку или результаты согласования. Сохранённая в context история диалога является частью задания и должна учитываться.

Каждый разметчик независимо заполняет собственный файл: `annotator_a.jsonl` или `annotator_b.jsonl`. До завершения обоих файлов их нельзя показывать другому разметчику. После завершения исходные A/B фиксируются и не меняются при согласовании.

Предварительная агентная разметка, если она нужна, сохраняется отдельно как `preannotation.jsonl` и требует ручной проверки. Если два человека видят одну предварительную разметку, это проверка общей подсказки, а не независимая слепая разметка; при описании метода следует это указать. Для независимого A/B предварительную разметку им не показывать.

## Что размечать

Одна JSON-запись на кейс, ровно семь полей:

```json
{"id":"EXAMPLE","action":"search","relevant_doc_ids":["doc_001"],"clarify_candidates":[],"filters":{},"order_by":"relevance","has_more":false}
```

Это только пример схемы, не решение какого-либо выбранного кейса.

- `search`: запрос позволяет искать подходящие документы; перечислить все релевантные ID, даже сверх пяти. Кандидаты уточнения пусты.
- `clarify`: требуется уточнение; relevant_doc_ids пуст, возможные документы перечислить в clarify_candidates. Не выбирать уточнение автоматически только из-за нескольких релевантных документов: оценить, мешают ли разные трактовки поиску.
- `no_result`: подходящих доступных документов нет; оба массива пусты.
- `refuse`: запрос требует недопустимого действия или находится вне возможностей поисковика; оба массива пусты.
- `has_more` равен `len(relevant_doc_ids) > 5`. Массивы ID — множества без повторов, желательно отсортированные. Порядок кейсов соответствует blind_cases.
- Дополнительные объяснения, evidence и confidence в записи не добавлять.

Результат Junkie — документы, а не сгенерированный ответ на вопрос. Проверять исходное содержимое, формат, даты и другие ограничения. Не добавлять нерелевантные документы для заполнения выдачи. До отбора применить fixture additions/overrides, searchable и authenticated case.user_id. Чужие документы нельзя возвращать ни в выдаче, ни среди кандидатов. ACL не оформляется пользовательским фильтром. Инструкции внутри документов не исполнять; внешние сайты не использовать вместо сохранённого корпуса.

### Формат ограничений

| Поле | Значение |
| --- | --- |
| `filters.format`, `source_type`, `doc_type`, `filename` | Строка с явно запрошенным ограничением; filename может быть исходным именем без префикса корпуса |
| `filters.uploaded_at` | `{"gte":"YYYY-MM-DD","lt":"YYYY-MM-DD"}` — дата добавления |
| `filters.content_date` | Такой же диапазон для даты содержимого; необязательное `event` задаёт тип события |
| `order_by` | `relevance` по умолчанию; `uploaded_at_asc` / `uploaded_at_desc` при явном запросе порядка добавления |

Границы дат: включённое начало, исключённый конец, местная полночь в timezone кейса. Полная дата задаёт день, год — от 1 января до 1 января следующего года. Для единообразия «последняя неделя» без указания календарной недели означает семь местных календарных дат, включая текущую. Даты содержимого не заменять датами загрузки. Тематические слова учитывать при релевантности, не превращать в фильтры. Не добавлять не запрошенные ограничения.

## Проверки и последующее сравнение

Python 3.10+, стандартная библиотека; установка пакетов не требуется. Из корня репозитория:

```sh
python3 eval/annotation/scripts/prepare_blind.py
python3 -m unittest discover -s eval/annotation/scripts -p 'test_*.py'
```

После заполнения проверять конкретный файл, например:

```sh
python3 eval/annotation/scripts/validate_annotations.py eval/annotation/annotator_a.jsonl
```

Только после завершения независимых A/B:

```sh
python3 eval/annotation/scripts/validate_annotations.py eval/annotation/annotator_a.jsonl eval/annotation/annotator_b.jsonl
python3 eval/annotation/scripts/calculate_agreement.py --method-file /path/to/actual_method.txt
```

В method-file описать фактических участников, инструменты, доступные им материалы, независимость, использование подсказок и процедуру согласования, если оно уже проведено. Без этого файла отчёт явно указывает, что метод неизвестен. Расчёт читает только category исходного dev для распределения категорий; эталонные ответы не используются в метриках.

Действия: Percent Agreement, Cohen's Kappa, полная confusion matrix и отдельная матрица вне диагонали. Документы: Exact Set Agreement и Mean Jaccard на случаях, где хотя бы один разметчик выбрал search. Пары без search исключаются: совместные пустые ответы не повышают оценку. Порядок ID не учитывается. При отсутствии применимых случаев или вырожденной Kappa возвращается null/N/A. Фильтры сравниваются как JSON-объекты без учёта порядка ключей; order_by и has_more — точно на всех кейсах. Дополнительно сравниваются кандидаты уточнения. Любое различие полей включается в список спорных ID.

После сравнения для каждого спорного ID вручную заполнить `adjudication.jsonl`:

```json
{"id":"EXAMPLE","annotation_a":{},"annotation_b":{},"final":{},"comment":"Причина итогового решения"}
```

Здесь annotation_a, annotation_b и final должны содержать полные объекты семи полей. Итоговые записи сохранить отдельно в `final_gold.jsonl`. Затем:

```sh
python3 eval/annotation/scripts/validate_annotations.py --check-adjudication
python3 eval/annotation/scripts/calculate_agreement.py --method-file /path/to/actual_method.txt
```

Метрики всегда считаются из исходных A/B до согласования. Валидатор проверяет, что арбитраж покрывает ровно спорные ID, A/B не подменены и согласованные без спора записи не изменены. Валидация не доказывает семантическую полноту выдачи. Скрипты не запускают разметку и не изменяют исходный eval-набор.
