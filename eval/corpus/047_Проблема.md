# Issue: macOS теряет маршрут к Tailscale MagicDNS (100.100.100.100) при реконнекте сети/VPN

## Кратко
На macOS при некоторых событиях (Wi‑Fi off/on, sleep/wake, реконнект VPN, иногда `tailscale down/up`) **пропадает/переопределяется host‑route к `100.100.100.100`** (MagicDNS Tailscale). В результате **становится недоступен MagicDNS**, из‑за чего **подвисают** `ssh`/`dscacheutil`/`dig @100.100.100.100` и “ломается подключение по имени” (например `example-workstation.tailnet.example.invalid`), хотя tailnet как таковой может оставаться рабочим.

---

## Контекст
Используем одновременно:

- **Amnezia VPN** — full tunnel через split `/1` маршруты (`0/1` и `128/1` через `utun` Amnezia).
- **Tailscale** — доступ к lab‑tailnet (`100.64.0.0/10`) + **MagicDNS** (внутренние имена, домен `tailnet.example.invalid`).
- Нужна возможность подключаться **по имени**, а не по IP.

Что делалось во время отладки (важно для хронологии):
- Настраивались **исключения** в Amnezia (split tunneling включён).
- В процессе диагностики **сбрасывались “плохие” host‑routes** (которые иногда появлялись и перетягивали трафик tailnet на `en0`).
- На Wi‑Fi был **вручную задан DNS** (`1.1.1.1`, `8.8.8.8`) для стабилизации глобального резолвинга.

**Файл `/etc/resolver/*` НЕ использовался.**

---

## Симптомы
После одного из событий:
- реконнект Amnezia (disconnect/connect),
- `tailscale down && tailscale up`,
- выключение/включение Wi-Fi,
- sleep / wake,
- смена сети,

наблюдается:

1) Подключение по имени начинает **висеть**:
- `ssh example-workstation` (или `ssh example-workstation.tailnet.example.invalid`) висит, пока не прервёшь.
- `dscacheutil -q host -a name example-workstation.tailnet.example.invalid` висит.
- `dig example-workstation.tailnet.example.invalid @100.100.100.100` таймаутится/висит.
- `nc -vz 100.100.100.100 53` висит (TCP/53).

2) При этом:
- `tailscale status` может выглядеть “нормально”.
- Доступ по tailnet IP иногда продолжает работать (например `ping 100.64.0.7`).
- Интернет может быть рабочим (например `dig google.com` через `1.1.1.1`).

Итого: внешне похоже на DNS‑проблему, но ключевое — **MagicDNS endpoint недоступен по сети**.

---

## Ключевой адрес
`100.100.100.100` — MagicDNS endpoint Tailscale.

Если он недостижим, то:
- системный резолвер (mDNSResponder) зависает на запросах tail‑имён,
- резолвинг `*.tailnet.example.invalid` ломается,
- `ssh` по имени “как будто подвисает”.

---

## Диагноз: маршрут к 100.100.100.100 уезжает на en0
Главный индикатор — вывод:

```bash
route -n get 100.100.100.100
```

### Нормально (работает)
Ожидаем, что маршрут идёт через utun Tailscale (у нас это был `utun6`, но номер может меняться):

```text
interface: utun6
```

В этом состоянии запросы к MagicDNS отвечают:

```bash
dig example-workstation.tailnet.example.invalid @100.100.100.100
dscacheutil -q host -a name example-workstation.tailnet.example.invalid
```

### Плохо (сломано)
После Wi‑Fi off/on или реконнекта VPN наблюдали:

```text
gateway: 198.51.100.1
interface: en0
```

То есть macOS начинает маршрутизировать `100.100.100.100` “как обычный интернет‑хост” через Wi‑Fi, и MagicDNS становится недоступен:

```bash
dig example-workstation.tailnet.example.invalid @100.100.100.100   # timeout/hang
nc -vz 100.100.100.100 53                    # hang
```

---

## Почему это не “просто DNS”
Мы отдельно проверяли, что сеть/интернет работает:

- `dig google.com @1.1.1.1` отвечал корректно даже в моменты, когда ломался резолвинг tail‑имён.
- Пинг внешних IP (`8.8.8.8`) проходил.
- Проблема воспроизводилась как **network/routing issue именно для `100.100.100.100`**.

То есть DNS‑симптомы — следствие того, что **DNS endpoint Tailscale физически недостижим** из‑за неверного маршрута.

---

## Воспроизведение (минимальный сценарий)
1) Дойти до рабочего состояния (Amnezia + Tailscale, имена резолвятся).
2) Зафиксировать, что маршрут к MagicDNS правильный:

```bash
route -n get 100.100.100.100
```

3) Выключить/включить Wi‑Fi (или выполнить reconnect Amnezia).
4) Повторить проверку маршрута.

Ожидаем, что иногда он станет через `en0`:

```text
interface: en0
gateway: 198.51.100.1
```

И далее:

```bash
dig example-workstation.tailnet.example.invalid @100.100.100.100   # timeout
```

---

## Важное наблюдение: это происходит даже без Amnezia
Сбой воспроизводился **только переключением Wi‑Fi**, без дополнительных “fixes” и без `/etc/resolver`.

Это указывает, что первопричина — **пересборка routing table в macOS при network rebind**, в ходе которой **host‑route к `100.100.100.100` теряется/замещается**.

---

## Почему `tailscale down/up` лечит (workaround)
Команда:

```bash
tailscale down
tailscale up
```

восстанавливает корректный host‑route:

- до: `100.100.100.100 -> en0`
- после: `100.100.100.100 -> utun (tailscale)`

После этого сразу оживают:

```bash
dig example-workstation.tailnet.example.invalid @100.100.100.100
dscacheutil -q host -a name example-workstation.tailnet.example.invalid
ssh example-workstation
```

**Но это workaround** (рестарт сервиса) и не подходит как “правильный” фикс для гайда.

---

## Дополнительный контекст из отладки: “плохие /32 маршруты”
Отдельно ловили ситуацию, когда появлялись более приоритетные маршруты (`/32`) к tailnet IP (например `100.64.0.7/32`) через `en0` (gateway `198.51.100.1`), которые перекрывали общий `100.64/10 -> utun(tailscale)`.

Пример симптома:
- `netstat -rn | grep 100` показывал `100.64.0.7/32 -> 198.51.100.1 en0`, из‑за чего pings/ssh на этот узел не работали, даже если tailnet маршрут был настроен.

Эта проблема решалась сбросом/очисткой конкретных host‑routes и корректной настройкой исключений в Amnezia, но **основной issue про MagicDNS — именно про `100.100.100.100`**.

---

## Проверочный чек‑лист
Когда “сломалось подключение по имени”:

1) Проверить маршрут к MagicDNS:

```bash
route -n get 100.100.100.100
```

Если `interface: en0` — это наш кейс.

2) Проверить доступность MagicDNS напрямую:

```bash
dig example-workstation.tailnet.example.invalid @100.100.100.100
nc -vz 100.100.100.100 53
```

3) Проверить, что tailnet маршрут жив:

```bash
netstat -rn | grep 100.64
```

## Открытые вопросы / куда копать
- Почему macOS при Wi‑Fi rebind иногда теряет host‑route к `100.100.100.100`?
- Можно ли заставить Tailscale автоматически восстанавливать host‑route на события network change?
- Можно ли “зафиксировать” host‑route без рестартов (например, через idempotent route‑fixer + launchd)?

## Приложение: команды, которые использовались при диагностике
```bash
# маршруты
netstat -rn | grep 100
netstat -rn | grep default
route -n get default
route -n get 100.100.100.100

# DNS/резолвинг
scutil --dns
dscacheutil -q host -a name example-workstation.tailnet.example.invalid
dig google.com
dig google.com @1.1.1.1
dig example-workstation.tailnet.example.invalid @100.100.100.100
nslookup google.com

# проверка доступности порта DNS
nc -vz 100.100.100.100 53

# тест сети/MTU
ping -D -s 1200 8.8.8.8
```
