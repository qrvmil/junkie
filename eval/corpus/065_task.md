# Домашнее задание: виртуальный курьер

**ROS 2 Jazzy · Python · четыре ноды**

**Срок сдачи: 20 октября 2026 года, 23:59 МСК. Максимум: 120 баллов.**

На семинаре мы начнём эту работу: создадим свой пакет и ноду с таймером и публикацией состояния. Дома вы допишете остальные части и проверите систему целиком.

В этой работе вы используете пакеты, сообщения, топики, сервис, action, параметры и таймеры. Данные курьера — названия станций и целые числа. Программы вы пишете на Python с помощью `rclpy`. Справка по методам и обработке событий — в [HOWTO.md](HOWTO.md).

## Что вы сделаете

Вы напишете четыре ноды ROS 2. Вместе они будут выполнять маршрут виртуального курьера: получать список станций, отправлять курьера на следующую станцию, сообщать о ходе поездки и останавливаться по запросу отмены.

Станции обозначаются словами: `warehouse`, `room_a`, `room_b`. В начале курьер находится на складе — `warehouse`.

Одна поездка занимает 20 срабатываний таймера. Таймер срабатывает раз в 0,2 секунды. На первом срабатывании выполнено 1 из 20 шагов, на десятом — 10 из 20, на двадцатом поездка завершена. Только после завершения обновляется название последней достигнутой станции. Это условная модель поездки: координаты, скорость и показания датчиков в ней не используются.

Пример полного маршрута:

```text
warehouse → room_a → room_b → warehouse
```

Оператор задаёт название маршрута. Система сама получает его содержимое и выполняет все поездки по порядку. Для полного маршрута поездок три: в `room_a`, затем в `room_b`, затем в `warehouse`.

## Как связаны части системы

![Схема взаимодействия четырёх нод](assets/interaction.svg)

Оператор отправляет название маршрута диспетчеру. Диспетчер запрашивает список станций у каталога, выдаёт команды курьеру и получает его состояние. По сообщениям о прибытии он выбирает следующую станцию, а оператору передаёт прогресс и результат маршрута.

## Создайте и соберите пакет

Для этой работы используйте выданный контейнер с ROS 2 Jazzy. Образ окружения закреплён в `Dockerfile`. Соберите и запустите контейнер командами из `README.md`.

Все команды `source`, `ros2` и `colcon` в условии выполняются внутри этого контейнера. Папка задания смонтирована в нём как `/work/courier_ws`. Исходники можно редактировать обычным редактором на компьютере.

В стартовом наборе есть пакет `courier_interfaces` с форматами данных и файл `config/routes.yaml` с маршрутами. Создайте рядом свой пакет:

```bash
source /opt/ros/jazzy/setup.bash
cd /work/courier_ws/src
ros2 pkg create courier_nodes --build-type ament_python \
  --license Apache-2.0 --dependencies rclpy courier_interfaces action_msgs python3-yaml
```

Папка `courier_nodes` после команды создания — корень пакета, а вложенная папка с тем же именем — Python-модуль. Во вложенной папке создайте четыре файла:

```text
courier_nodes/
├── package.xml
├── setup.py
├── setup.cfg
├── resource/
│   └── courier_nodes
└── courier_nodes/
    ├── __init__.py
    ├── route_server.py
    ├── robot.py
    ├── route_manager.py
    └── operator.py
```

В каждом файле должны быть класс ноды и функция `main`. Используйте образец с семинара: подготовить ROS, создать ноду, запустить обработку событий, корректно завершить работу.

В `setup.py` зарегистрируйте четыре точки запуска:

```python
'route_server = courier_nodes.route_server:main',
'robot = courier_nodes.robot:main',
'route_manager = courier_nodes.route_manager:main',
'operator = courier_nodes.operator:main',
```

Эти строки добавляются в список `entry_points['console_scripts']`. Не заменяйте ими весь файл `setup.py`.

Соберите workspace из его корня:

```bash
cd /work/courier_ws
colcon build --symlink-install --packages-up-to courier_nodes
```

Для запуска откройте отдельные терминалы на компьютере и подключитесь к работающему контейнеру через `docker exec`, как показано в `README.md`. В каждом выполните:

```bash
source /opt/ros/jazzy/setup.bash
cd /work/courier_ws
source install/local_setup.bash
```

После этого в одном терминале запускается одна нода. Для этой домашней работы достаточно четырёх команд `ros2 run`; собственный launch-файл не требуется.

## Нода 1. Каталог маршрутов

Файл: `route_server.py`. Команда запуска: `ros2 run courier_nodes route_server`.

Создайте сервис `/courier/get_route` типа `courier_interfaces/srv/GetRoute`.

В запросе одно поле: `route_name` — название маршрута. Ответ содержит:

| Поле | Содержание |
|---|---|
| `found` | `true`, если маршрут найден; иначе `false` |
| `destinations` | Список станций назначения в нужном порядке |
| `message` | Короткое пояснение ответа |

Готовая таблица маршрутов:

| Название | Станции назначения | Число поездок |
|---|---|---|
| `short` | `room_a`, `warehouse` | 2 |
| `full` | `room_a`, `room_b`, `warehouse` | 3 |

Начальный `warehouse` не входит в список назначений: курьер уже находится там. Для `full` нужно выполнить три поездки, а не четыре.

Реализуйте следующие действия:

1. При запуске загрузите маршруты из YAML-файла, указанного параметром `routes_file`. Значение по умолчанию — `config/routes.yaml`; ноду запускайте из `/work/courier_ws`. Корневой раздел файла называется `routes`. Как прочитать его с помощью `yaml.safe_load`, объяснено в [HOWTO.md](HOWTO.md).
2. Зарегистрируйте сервис.
3. В обработчике запроса найдите маршрут по имени.
4. Если он найден, верните `found=true` и его станции.
5. Если он не найден, верните `found=false`, пустой список и пояснение.
6. После ответа продолжайте принимать запросы.

Сам каталог не запускает поездки. Его работа заканчивается возвратом списка.

Проверка:

```bash
ros2 service call /courier/get_route courier_interfaces/srv/GetRoute \
  "{route_name: 'full'}"
```

В ответе должны быть три станции. Повторите запрос с именем `missing`: должен вернуться отказ, а нода должна продолжить работать.

## Нода 2. Курьер

Файл: `robot.py`. Команда запуска: `ros2 run courier_nodes robot`.

Эта нода моделирует одну поездку. Она не знает, сколько станций в маршруте и куда нужно ехать после текущей поездки.

### Получайте команды

Создайте подписку на `/courier/command` типа `courier_interfaces/msg/RobotCommand`.

| Поле | Значение |
|---|---|
| `command_id` | `uint32`: положительный номер команды |
| `target_station` | Название станции назначения |
| `stop` | `false` — начать поездку; `true` — остановить её |

В проверках используются корректные команды: известная станция для поездки, пустая цель для остановки и положительный номер. Проверку произвольных повреждённых команд реализовывать не требуется.

Например, команда с номером 7, станцией `room_a` и `stop=false` означает: «выполни поездку в `room_a` и сообщай её состояние с номером 7».

Номер нужен для различения поездок: старое сообщение о прибытии по команде 7 не должно завершать новую поездку по команде 8. Диспетчер выдаёт новый номер для каждой команды, включая остановку. Номера возрастают на 1 и не сбрасываются при новом маршруте: после команд 1, 2 и 3 следующий маршрут начинает с команды 4. Номера действуют в пределах одного запуска системы; сохранение между запусками не требуется.

### Публикуйте состояние

Создайте publisher в `/courier/state` типа `courier_interfaces/msg/RobotState` и таймер с периодом 0,2 секунды.

| Поле | Значение |
|---|---|
| `command_id` | Номер последней принятой команды; до первой команды — 0 |
| `last_station` | Последняя станция, до которой поездка полностью завершена |
| `target_station` | Станция текущей или только что завершённой поездки; при простое после запуска или остановки — пустая строка |
| `state` | `IDLE`, `MOVING` или `ARRIVED` |
| `ticks_done` | Сколько шагов выполнено: от 0 до 20 |
| `ticks_total` | Число шагов полной поездки: 20 |

### Правила поведения

1. При запуске: `last_station=warehouse`, `state=IDLE`, `ticks_done=0`.
2. На каждом срабатывании таймера публикуйте состояние, в том числе при простое.
3. При новой команде поездки сохраните её номер и цель, установите `MOVING` и обнулите `ticks_done`.
4. Пока состояние `MOVING`, каждое срабатывание таймера увеличивает `ticks_done` на 1.
5. При достижении 20 шагов установите `last_station=target_station`, `state=ARRIVED`. Продолжайте публиковать это состояние до новой команды.
6. Повторное получение команды с тем же номером, что у последней принятой команды, не должно начинать поездку заново.
7. При `stop=true` примите новый номер команды, установите `IDLE`, очистите цель и обнулите прогресс. Последняя достигнутая станция не меняется.
8. Если новая цель совпадает с `last_station`, сразу сообщите `ARRIVED` с прогрессом 20 из 20.

Если поездку отменили на восьмом шаге, станция назначения ещё не достигнута. Следующая поездка в условной модели начинается с нулевого прогресса.

Для обоих топиков задайте одинаковый профиль: хранить последние 10 сообщений, использовать reliable и volatile. Можно передать изученный аргумент `10`; в `ANSWERS.md` объясните, какие политики он задаёт.

### Проверка отдельно от остальных нод

В одном терминале запустите `robot`. Во втором смотрите состояние:

```bash
ros2 topic echo /courier/state
```

В третьем отправьте одну команду:

```bash
ros2 topic pub --once /courier/command courier_interfaces/msg/RobotCommand \
  "{command_id: 1, target_station: 'room_a', stop: false}"
```

Должны появиться состояния `MOVING`, увеличение прогресса и затем `ARRIVED`. Отправьте ту же команду ещё раз: прогресс не должен обнулиться.

После прибытия в `room_a` начните новую поездку:

```bash
ros2 topic pub --once /courier/command courier_interfaces/msg/RobotCommand \
  "{command_id: 2, target_station: 'room_b', stop: false}"
```

Дождитесь состояния `MOVING` и отправьте остановку до завершения 20 шагов:

```bash
ros2 topic pub --once /courier/command courier_interfaces/msg/RobotCommand \
  "{command_id: 3, target_station: '', stop: true}"
```

После остановки должно публиковаться `IDLE`, а `last_station` должен остаться `room_a`. Перед запуском всей системы перезапустите курьера, чтобы вернуть начальное состояние и номера команд.

## Нода 3. Диспетчер

Файл: `route_manager.py`. Команда запуска: `ros2 run courier_nodes route_manager`.

Создайте в этой ноде:

- клиент сервиса `/courier/get_route`;
- publisher `/courier/command`;
- подписку `/courier/state`;
- action-сервер `/courier/execute_route` типа `courier_interfaces/action/ExecuteRoute`.

### Что содержит action

В goal одно поле: `route_name` — название маршрута.

Feedback:

| Поле | Значение |
|---|---|
| `visited_count` | Число полностью завершённых поездок текущего маршрута |
| `total_count` | Число поездок в маршруте |
| `target_station` | Станция текущей поездки |
| `leg_progress` | Прогресс текущей поездки, целое число от 0 до 100 |

Result:

| Поле | Значение |
|---|---|
| `visited_count` | Число полностью завершённых поездок |
| `last_station` | Последняя достигнутая станция |
| `message` | Пояснение: маршрут выполнен, отменён или не найден |

Кроме этих полей, action передаёт признак завершения: `SUCCEEDED`, `CANCELED` или `ABORTED`. Получение согласия принять goal ещё не является успешным завершением маршрута.

### Выполнение обычного маршрута

1. Примите goal с названием маршрута. Одновременно допускается один маршрут; второй goal во время работы отклоните. Пустое имя также отклоните.
2. Запросите маршрут у каталога. Используйте асинхронный запрос: пока ответ не пришёл, нода должна продолжать обрабатывать другие события. С момента принятия goal и до его завершения нода считается занятой, включая ожидание каталога и остановки.
3. Если маршрут не найден, завершите action как `ABORTED`. Команд поездки отправлять не нужно.
4. Если маршрут найден, сохраните список назначений и обнулите число завершённых поездок.
5. Создайте номер команды и отправьте первую цель курьеру. Отправьте команду один раз; дальше ждите состояние.
6. Обрабатывайте сообщения курьера. Для текущей поездки используйте только сообщения с её номером команды.
7. По каждому сообщению `MOVING` текущей команды отправляйте feedback. Вычисляйте `leg_progress = ticks_done * 100 // ticks_total`. Например, 8 из 20 шагов — это 40% текущей поездки. `visited_count` пока не включает незавершённую поездку.
8. При `ARRIVED` увеличьте число завершённых поездок один раз. Отправьте feedback с достигнутой целью и прогрессом 100%, затем отправьте следующую цель с новым номером. Повторные сообщения `ARRIVED` старой поездки не должны увеличивать счётчик.
9. Feedback о последнем прибытии является финальным: `visited_count=total_count`, последняя цель и прогресс 100%. Затем завершите action как `SUCCEEDED` и верните result.
10. После завершения снова принимайте новые маршруты. Счётчик посещений для нового goal начинается с нуля; курьер остаётся на последней достигнутой станции.

Не завершайте поездку по собственному четырёхсекундному таймеру в этой ноде. Сообщение курьера о прибытии является подтверждением её завершения.

### Отмена

1. При запросе отмены активного action прекратите отправку новых целей.
2. Отправьте курьеру команду `stop=true` с новым номером.
3. Дождитесь `RobotState` с номером этой команды и состоянием `IDLE`.
4. Завершите action как `CANCELED`.
5. В result укажите число подтверждённых завершённых поездок и `last_station` из сообщения, подтвердившего остановку. Незавершённая поездка в счётчик не входит. Если сообщение `ARRIVED` текущей поездки пришло во время остановки, учтите эту поездку один раз, но следующую не отправляйте.

Отмену можно запросить и во время ожидания каталога. В этом случае тоже остановите курьера и дождитесь подтверждения. Пришедший позже ответ каталога не должен запустить поездку.

До подтверждения остановки action остаётся активным. После `CANCELED` команд следующих поездок этого маршрута быть не должно.

### Работа с action-сервером

Создайте сервер с помощью `rclpy.action.ActionServer`. Задайте обработчики приёма цели и отмены. По умолчанию сервер принимает все цели; ваш обработчик должен отклонять пустое имя и вторую цель, в том числе во время ожидания каталога и подтверждения остановки.

Во время ожидания маршрута, прибытия или остановки нода должна обрабатывать новые сообщения и запросы отмены. Обычный callback не должен ждать в цикле `while` или вызывать `time.sleep`. Даже `async def` не освобождает executor, если внутри нет подходящего `await`. В [HOWTO.md](HOWTO.md) описан способ ожидания события с `rclpy.task.Future` и выбор callback group для action-сервера.

Восстанавливать маршрут после выключения или перезапуска нод не требуется. Проверки выполняются с запущенными каталогом и курьером.

## Нода 4. Оператор

Файл: `operator.py`. Оператор запускает маршрут из вашей Python-программы. Создайте клиента с помощью `rclpy.action.ActionClient`; нужные методы описаны в [HOWTO.md](HOWTO.md).

1. Создайте action-клиент `/courier/execute_route`.
2. Прочитайте параметр `route_name`; по умолчанию используйте `short`.
3. Дождитесь доступности action-сервера. Оператор должен работать и тогда, когда сервер запустился позже него.
4. Отправьте один goal и выведите, принят он или отклонён.
5. Для каждого feedback выводите число завершённых поездок, текущую цель и прогресс.
6. Получите окончательный result и выведите причину завершения и его поля.
7. Добавьте параметр `cancel_after_feedback`, целое неотрицательное число. Значение 0 означает обычное выполнение. Положительное значение N означает: после N сообщений feedback один раз запросить отмену и затем дождаться результата. Считайте все сообщения feedback, включая сообщение при завершении маршрута. Чтобы проверить отмену во время поездки, используйте `full` и N = 5.
8. При отклонённом goal выведите отказ и завершитесь: ожидать result у непринятого goal не нужно. После вывода result завершите программу оператора. Остальные ноды продолжают работать.

Пример обычного запуска:

```bash
ros2 run courier_nodes operator --ros-args -p route_name:=full
```

Пример запуска с отменой:

```bash
ros2 run courier_nodes operator --ros-args \
  -p route_name:=full -p cancel_after_feedback:=5
```

Точный текст вывода выбираете вы. По нему должно быть понятно: goal принят, прогресс меняется, операция завершилась с конкретным результатом. В выводе используйте значения, полученные от сервера.

## В каком порядке выполнять работу

1. Создайте и соберите пакет, проверьте точки запуска.
2. Напишите простейший `robot`: пока без приёма команд, с таймером и публикацией состояния `IDLE`.
3. Добавьте в `robot` поездку по команде, счётчик шагов и остановку. Проверьте ноду отдельно.
4. Напишите `route_server`, проверьте оба маршрута и неизвестное имя.
5. Напишите обычное прохождение маршрута в `route_manager`. Сначала проверьте его через CLI:

   ```bash
   ros2 action send_goal /courier/execute_route \
     courier_interfaces/action/ExecuteRoute "{route_name: 'short'}" --feedback
   ```

6. Добавьте feedback, обработку неизвестного маршрута и отклонение второго goal.
7. Напишите `operator` и проверьте обычный запуск из своей ноды.
8. Добавьте отмену в сервер и клиент, проверьте остановку курьера.
9. Запустите проверки, исправьте ошибки и заполните `ANSWERS.md`.

Пункты 1–2 начинаем на семинаре. К концу совместной части ваш собственный пакет должен запускать ноду, которая периодически публикует корректное сообщение. Начать приём команд можно, если останется время.

## Проверка программы

В терминале внутри контейнера выполните:

```bash
cd /work/courier_ws
bash check.sh
```

Скрипт сам собирает пакеты и запускает ваши ноды. Тесты проверяют ответы сервиса, команды, состояния и завершение action.

Полный набор учительских проверок выполняется на сервере, результаты появляются в Manytask. Локальная команда `bash check.sh` проверяет сборку и ваши тесты пакета. Провал одного серверного критерия не останавливает остальные проверки. Ещё до 5 баллов преподаватель выставляет за ответы в `ANSWERS.md`.

Каталог должен возвращать станции `short` и `full` в заданном порядке. Для `missing` он возвращает отказ и пустой список, после чего продолжает отвечать на запросы.

Курьер должен завершать поездку после 20 шагов, сохранять прогресс при повторной команде с тем же номером и подтверждать остановку состоянием `IDLE`. При остановке последняя достигнутая станция сохраняется. Команда поездки в уже достигнутую станцию сразу даёт `ARRIVED` с прогрессом 20 из 20.

Диспетчер должен выполнять `short` за две поездки, а `full` — за три. Оба маршрута заканчиваются на `warehouse` со статусом `SUCCEEDED`. Для `missing` результат — `ABORTED` с нулём завершённых поездок, без команды движения. Пустое имя и второй goal во время активного маршрута отклоняются. Это относится и к ожиданию ответа каталога, и к ожиданию подтверждения остановки.

Отдельные сценарии проверяют повторные и старые сообщения состояния: они не должны дважды засчитать прибытие или завершить новую поездку. После завершения первого маршрута система должна принять следующий; его счётчик поездок начинается с нуля, а номера команд продолжают возрастать.

Для проверки отмены оператор запускается с `route_name:=full` и `cancel_after_feedback:=5`. Диспетчер прекращает выдавать цели, отправляет остановку и возвращает `CANCELED` только после подтверждения `IDLE` с нужным номером команды. Проверяется и отмена до ответа каталога: поздний ответ не должен начать поездку. Если прибытие текущей поездки подтверждено во время остановки, оно учитывается один раз. После результата курьер продолжает публиковать `IDLE`, а новых поездок отменённого маршрута не появляется.

### Ручной запуск для диагностики

Команды сборки и запуска приведены в выданном `README.md`. Для наблюдения за всей системой запустите каталог, курьера и диспетчер в отдельных терминалах:

```bash
ros2 run courier_nodes route_server
ros2 run courier_nodes robot
ros2 run courier_nodes route_manager
```

Оператор запускается в четвёртом терминале. Во время работы всей системы команды курьеру отправляет диспетчер: ручные публикации из раздела про курьера завершите до этого запуска.

Можно проверить action напрямую:

```bash
ros2 action send_goal /courier/execute_route \
  courier_interfaces/action/ExecuteRoute "{route_name: 'short'}" --feedback
```

При проверке независимых сценариев перезапускайте три основные ноды, чтобы начать со склада и начальных номеров команд. Для повторного маршрута оставьте систему работающей и запустите оператор ещё раз.

### Совместная работа всех четырёх нод — 20 баллов

1. Оператор с `route_name:=full` запускает полный маршрут. Курьер посещает `room_a`, `room_b` и `warehouse` в таком порядке. Оператор получает feedback и успешный результат с тремя завершёнными поездками и конечной станцией `warehouse`, затем завершает работу.
2. Оператор с `route_name:=full` и `cancel_after_feedback:=5` запускает новый маршрут и запрашивает отмену. Курьер останавливается; оператор получает окончательный результат `CANCELED` и завершает работу. Новых поездок отменённого маршрута не появляется.
3. Оператор без параметров запускает `short`. Система успешно выполняет две поездки и возвращает результат с двумя завершёнными поездками и конечной станцией `warehouse`. Номера команд продолжают возрастать.

За прохождение всего сценария начисляются 20 баллов. Если он не пройден, баллы за сборку, отдельные ноды и ответы сохраняются.

## Приложение: точные форматы данных

Эти определения уже находятся в пакете `courier_interfaces`. Их менять не нужно. Они приведены здесь, чтобы можно было проверить названия и типы полей.

`msg/RobotCommand.msg`:

```text
uint32 command_id
string target_station
bool stop
```

`msg/RobotState.msg`:

```text
uint32 command_id
string last_station
string target_station
string state
uint16 ticks_done

```

`srv/GetRoute.srv` — над разделителем запрос, под ним ответ:

```text
string route_name
---
bool found
string[] destinations
string message
```

`action/ExecuteRoute.action` — по порядку goal, result, feedback:

```text
string route_name
---
uint32 visited_count
string last_station
string message
---
uint32 visited_count
uint32 total_count
string target_station
uint8 leg_progress
```
