# Оценивание КТ3

Здесь оценщик сохранённых результатов, LLM-судья и семь сценариев.
Runner, бейзлайны и Junkie подключаются отдельно. Измеренных результатов пока нет.
КТ2 и закрытая выборка не изменены.

## Запуск

Python 3.10+, без дополнительных пакетов. Команды из корня репозитория.

```bash
python -m unittest discover -s eval/kt3/tests
python -m eval.kt3.evaluate --run runs/b0/run.json --predictions runs/b0/search.jsonl --output runs/b0/report.json
```

Файлы результатов создаёт runner по [формату](FORMAT.md).
Оценщик не перезаписывает существующий отчёт. До включения ingestion/сценариев
они перечислены в `not_run`, а не считаются проверенными.

Полная команда (предельное ожидание добавления выбирается командой):

```bash
python -m eval.kt3.evaluate \
  --run runs/junkie/run.json \
  --predictions runs/junkie/search.jsonl \
  --clean-predictions runs/junkie/clean.jsonl \
  --ingestion-outputs runs/junkie/ingestion.jsonl \
  --ingestion-timeout-s "$INGESTION_TIMEOUT_S" \
  --scenario-outputs runs/junkie/scenarios.jsonl \
  --reviews runs/junkie/messages.jsonl \
  --reviews runs/junkie/metadata-review.jsonl \
  --output runs/junkie/report.json
```

В отчёте: общие метрики, категории, gold-действия, оценки каждого кейса,
проверки контракта, время, стоимость и хеши использованных файлов.
`eligible/scored/pending` — размеры выборок для проверки расчёта, не метрики качества.

## Судья для сообщений

Модель выбирается явно. `--prepare-only` сохраняет задачи без сети и ключа:

```bash
python -m eval.kt3.judge --predictions runs/junkie/search.jsonl \
  --model "$JUDGE_MODEL" --prepare-only --output runs/junkie/judge-tasks.jsonl
```

Платный запуск: убрать `--prepare-only`, задать `OPENROUTER_API_KEY` в окружении
и другой выходной файл, например `messages.jsonl`. `--max-calls` ограничивает
число проверок; `--max-output-tokens` — длину ответа судьи.

Судья проверяет только сообщение о других результатах, предложение сузить
поиск и полезность уточнения. Число/уникальность документов проверяет код.
Промпт лежит в `prompts/messages.txt`. Сохраняются модель, текст решения,
причина, хеши входа и промпта, токены и стоимость. Ошибка API/неверный JSON
оставляют оценку незавершённой. Повторы автоматически не запускаются.
LLM-оценка не является человеческой разметкой; перед отчётом стоит просмотреть
её объяснения на спорных ответах.

## Метаданные: ручная оценка

```bash
python -m eval.kt3.evaluate --run runs/junkie/run.json \
  --predictions runs/junkie/search.jsonl \
  --ingestion-outputs runs/junkie/ingestion.jsonl \
  --ingestion-timeout-s "$INGESTION_TIMEOUT_S" \
  --export-metadata-review runs/junkie/metadata-review.jsonl \
  --output runs/junkie/before-review.json
```

В форме указаны исходник и критерии КТ2. Проверяющий заполняет `reviewer`,
`fields.*.passed/reason`, для каждого тега — `supported`, `concept_id`, `reason`,
затем ставит `status: "ok"`. Синонимам присваивается один `concept_id`.
Нельзя считать тему/теги правильными только потому, что строки непустые.
Повторный расчёт с `--reviews` завершает соответствующие метрики.
Изменённый ответ или эталон требуют новой оценки.

## Правила подсчёта

- Отсутствующий/ошибочный ответ даёт 0 в применимых положительных метриках.
  Релевантность считается на gold=search, действие — на всех поисковых кейсах.
- Повторы занимают позиции, но не добавляют попаданий. Precision@5 делится на 5.
- `pending` означает отсутствие наблюдения или оценки, `not_applicable` —
  неприменимость. При `pending` итоговое среднее не публикуется по оставшимся кейсам.
- Сортировка дат: без сравнимых пар N/A, как в КТ2. Нахождение документов
  отдельно проверяют поисковые метрики.
- Для опечаток runner выполняет `clean_query` для тех же 11 кейсов в тех же
  условиях. ID сохраняются в отдельном `clean.jsonl`. Без файла Drop не измерен;
  пропущенная строка в переданном файле — неуспех. Drop — доля, для п.п. умножить на 100.
- P50/P95: полные успешные ответы, линейная интерполяция; сбои и пропуски
  показаны отдельно. Для ingestion требуется фактическая готовность к поиску.
  Квантили отдельных этапов не складываются. 45 секунд SLO не задают таймаут.
- Стоимость берётся из фактического usage, включая повторы. Без полной записи
  выводится известная часть и `cost_usd: null`. Судья учитывается отдельно.
- Отсутствие трейса не доказывает изоляцию архивов или устойчивость к injection.
  Наблюдаемая утечка фиксируется даже при неполном трейсе.

## Что передать разработчикам runner

1. [Формат](FORMAT.md): ответы, наблюдения адаптера, usage и метаданные запуска.
2. [Покрытие](COVERAGE.md): какие данные нужны каждой проверке.
3. `scenarios.json`: живые сценарии с сохранением фактических предыдущих ответов.
   `assert` и эталоны получает только оценщик. `max_steps` здесь считает вызовы
   инструментов, включая ошибки. Лимит вызовов модели/токенов runner задаёт отдельно.

В S05 сбой внедряется посередине выполнения. В S06 лимит инструментов снижен
до трёх, чтобы проверить остановку. S07 начинается без добавляемого документа.
DialogueSuccessRate относится к S01–S04; для всех семи есть `ScenarioSuccess`.
Проверки текстов в dev и успех живого сценария — отдельные результаты.
