# Знаменатели поисковых метрик

Подвыборка определяется эталоном до запуска, а не ответом модели или наличием
строки в результатах. Текущий dev содержит 140 кейсов: 116 `search`, 6 `clarify`,
9 `no_result`, 9 `refuse`. Ingestion оценивается отдельно.

## Определения

Обозначим S — все кейсы с `expected.action=search` и непустым набором релевантных
ID G. На каждом кейсе рассматриваются первые пять позиций ответа T; документы
не сортируются заново. Повторы занимают позиции, но не увеличивают число попаданий.
Позиция 6 не становится пятой после удаления повторов.

| Метрика | Значение кейса | Знаменатель среднего |
| --- | --- | --- |
| HitRate@5 | 1, если T пересекается с G, иначе 0 | Все S (сейчас 116) |
| MRR@5 | 1 / исходная позиция первого релевантного ID в T, иначе 0 | Все S |
| Recall@5 | Число разных релевантных ID в T / размер G | Все S |
| Precision@5 | Число разных релевантных ID в T / 5 | Все S |
| Action Accuracy | 1 при совпадении действия, иначе 0 | Все поисковые кейсы (сейчас 140) |
| Action Accuracy по классу | Та же проверка, отдельно для каждого gold-действия | Число кейсов соответствующего gold-класса |
| False Refusal Rate | 1, если корректно оформленный ответ имеет action=refuse, иначе 0 | Все S |

Четыре действия: `search`, `clarify`, `no_result`, `refuse`. `no_result` означает,
что в доступном архиве нет результата; `refuse` — отказ выполнять недопустимый
или неподдерживаемый запрос. Их не объединяют. `Answer/Clarify/Refuse` не являются
алиасами протокола. Ошибка, таймаут, отсутствие и невалидный ответ — исходы запуска,
а не дополнительные действия модели.

Для кейса из S неправильное действие, ошибка, таймаут, пропуск или невалидный ответ
дают нули во всех четырёх метриках ранжирования. Такие кейсы не исчезают из S.
В Action Accuracy технические неуспехи также дают 0. В False Refusal Rate
они не превращаются в отказ; их число видно в outcome_counts и Action Accuracy.
Правильные clarify/no_result/refuse оцениваются в выборе действия и не снижают
HitRate. Это не проверяет содержательную полезность уточняющего вопроса.

Каждая метрика выводит `value`, `sum` и `n`. `n=0` означает `value=null` (N/A),
а не 0% или 100%. Action Accuracy дополнительно публикуется по gold-классам,
чтобы преобладающие search-кейсы не скрывали ошибки редких действий.

Идеальная выдача даёт HitRate=1 и MRR=1. Precision@5 при одном релевантном
документе равна 0.2; Recall@5 при шести релевантных не превышает 5/6. Это
следствия исходных определений, а не ошибки. Цели ≥90% HitRate и ≥0.75 MRR
сохраняются; Precision и Recall не получают новый произвольный порог.

## Воспроизводимый расчёт

`score.py` реализует только шесть метрик из таблицы и разбиение Action Accuracy
по действиям. Это офлайн-оценщик готовых ответов, а не поисковик или benchmark.
Проверки источников, ACL, фильтров, overflow, инструментов, качества уточнения,
ingestion и задержек остаются отдельными проверками. Одного HitRate для
выполнения контракта недостаточно. Выдача длиннее пяти обрезается только для
расчёта @5; нарушение лимита должен отдельно зафиксировать контрактный оценщик.

Одна JSONL-строка на завершённый кейс:

```json
{"id":"E01","status":"ok","action":"search","result_doc_ids":["doc_001"]}
{"id":"E22","status":"ok","action":"clarify","result_doc_ids":[]}
{"id":"E23","status":"ok","action":"no_result","result_doc_ids":[]}
{"id":"E24","status":"ok","action":"refuse","result_doc_ids":[]}
{"id":"E02","status":"timeout"}
```

Это пример формата, не результаты прогона. Порядок ID в result_doc_ids —
фактический порядок выдачи; кандидаты уточнения не являются выдачей.
status принимает ok/error/timeout/missing/invalid. Для ok обязательны
action и result_doc_ids; у действий, отличных от search, выдача пустая.
Отсутствующая строка считается missing. Строка с известным id и неверной формой
ответа считается invalid. Неизвестные/повторные id, строки без id и повреждённый
JSON прерывают импорт: их нельзя надёжно сопоставить с заданиями.

```sh
python eval/annotation/scripts/validate_eval.py
python eval/metrics/score.py --predictions /path/to/predictions.jsonl
python -m unittest discover -s eval/metrics -p 'test_*.py'
```

По умолчанию берётся текущий `eval/queries/dev.jsonl`; `--cases` позволяет явно
выбрать другой зафиксированный набор. Отчёт печатается в stdout, входы не меняются.
Тест с синтетическими идеальными ответами из gold проверяет формулы и знаменатели.
Его результаты нельзя представлять как качество Junkie или baseline.
