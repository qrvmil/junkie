# ADR-001. LLM разбирает запрос, локальные инструменты выполняют поиск

Дата: 22.11.2026. Статус: принято для прототипа КТ3.

В исходной версии (full-01) поиск выполнялся одним планом. В [эксперименте 02](experiments/02.md) при неоднозначном открытии добавлен ограниченный выбор по карточкам; проверка ID из истории перенесена в код. Ниже зафиксировано исходное решение.

## Контекст

Нужно измерить B0, B1 и Junkie на одном корпусе и через один runner. В запросах
есть фильтры, опечатки, ссылки на прошлую выдачу и уточнения. При этом владелец,
состав выдачи, доступность источника и происхождение фрагмента должны проверяться
кодом. Качество семантического поиска ещё предстоит подтвердить замерами.

## Решение

Junkie использует LLM как планировщик: она возвращает проверяемый JSON с действием,
поисковыми словами и фильтрами. `search_documents` применяет ограничения владельца
и BM25; `get_document` повторно проверяет владельца. Карточки, фрагменты и сообщение
о большой выдаче формирует код. Модель может предложить близкие поисковые слова,
но не задаёт итоговые ID поисковой выдачи. Для прямого открытия промпт требует
выбирать ID из истории; код проверяет непустой ID и владельца, но принадлежность
ID прошлой выдаче пока не проверяет. Поэтому модель может открыть другой
доступный тому же владельцу документ; качество такого выбора оценивается отдельно.

B1 использует тот же поиск, заменяя планировщик правилами. Поэтому сравнение
B1/Junkie показывает эффект разбора запроса и диалога при общем ранжировании.
B0 отличается от B1 только подсчётом совпадений вместо BM25.

Первоначальный архив всех вариантов получает метаданные по правилам. LLM-метаданные
проверяются при добавлении документа. Хранение — файлы корпуса и индекс в памяти;
между репликами сценария сохраняются этот индекс и реальная история. Это граница
лабораторного прототипа, не замена целевому облачному хранилищу.

## Рассмотренные варианты

| Вариант | Почему не выбран сейчас | Когда пересмотреть |
|---|---|---|
| Только правила и BM25 | Это B1: нет использования истории и механизма полезного уточнения | Если LLM не даст улучшения целевых метрик, оправдывающего задержку и расход, оставить B1 основным вариантом |
| Передавать весь архив в LLM и просить готовый ответ | Расход растёт с архивом; сложнее проверять найденные ID, фрагменты и границы доступа | Если архив гарантированно мал и отдельный эксперимент покажет выигрыш при тех же проверках источников и доступа |
| Векторный или гибридный поиск сразу | Добавляет модель эмбеддингов, индекс и ещё один фактор сравнения до замера простого поиска | Если разбор провалов покажет, что правильный план не находит релевантные документы из-за отсутствия общих слов; проверить отдельной абляцией |
| Свободный агентный цикл | Для поиска нужны два читающих инструмента и короткий диалог; сложнее ограничить повторы и объяснить трассу | Если появятся задачи, где по результату нескольких инструментов нужно динамически выбирать следующий шаг |
| PostgreSQL и объектное хранилище уже в КТ3 | Для сравнения на зафиксированном локальном корпусе добавляют развёртывание без изменения проверяемой логики поиска | Перед подключением реальных пользователей, параллельных запросов и хранением между перезапусками |

## Последствия и проверки

- Выбор владельца и выдача источников не зависят от соблюдения моделью промпта.
  Невалидный план возвращает ошибку, а не исполняется частично.
- Общий код парсинга, фильтров и ранжирования упрощает сравнение. Результат
  всё равно относится к открытому dev-набору, на котором писались правила.
- BM25 ограничивает смысловой поиск: LLM может расширить запрос, но это
  не гарантирует нахождения документа без лексического пересечения.
- Проверка качества включает поисковые метрики, соблюдение фильтров, ACL,
  действия, многошаговые сценарии, задержку и стоимость. Решение не объявляется
  лучше B1 до фактического сравнения.
- Индекс в памяти не переживает перезапуск. URL представлены снимками HTML,
  шесть PNG не имеют OCR, длинные тексты для метаданных обрезаются. Эти ограничения
  сохраняются в отчёте и не подменяются эталонными метаданными.
